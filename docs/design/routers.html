Routers: four GL-SFT1200 Opals

One Portal in the hallway that is the only thing the school network ever sees, and one Tunnel per classroom. About 25 minutes per router the first time, 10 once you have done one. Everything here is the stock GL.iNet 4.x admin panel; no SSH, no LuCI, no custom firmware.

Before you start

  • Four Opals, four USB-C supplies rated 5 V / 3 A. The Opal's spec is 3 A; a 2 A phone charger browns out under load and the symptom is random reboots. A phone charger that says "5V⎓3A" is fine.
  • Four labels: PORTAL 192.168.80.1, TUNNEL 1 192.168.81.1, TUNNEL 2 192.168.82.1, TUNNEL 3 192.168.83.1. Put them on now; identical boxes get swapped.
  • The latest firmware file for GL-SFT1200 from dl.gl-inet.com/router/sft1200 (4.8.3 as of this writing; "Local Upgrade" file). Download it once on your laptop.
  • The passwords you will reuse, written down: the admin password (same on all four), the WormHole-Core backhaul password (long, only the Tunnels know it), and the WormHole classroom password (the Picos' wifi.json must match it; the flash script on the Pico fleet page writes it).
  • Ports on the Opal: one WAN port and one LAN port. The Burrow plugs into the Tunnel's LAN port. If you cable a Tunnel to the Portal, that cable goes Portal LAN → Tunnel WAN, and the Portal only has one LAN port, so at most one Tunnel can be cabled; the rest use the 5 GHz backhaul.

Step 0 · The same first five minutes on every router

  1. Power it, wait for the LED to settle (about a minute). Join its default Wi-Fi from your laptop: SSID GL-SFT1200-xxx, password goodlife (both printed on the bottom label).
  2. Open http://192.168.8.1. The first-run wizard asks for a language and an admin password. Use your shared admin password. There is no default admin password to remember; this is the only one.
  3. SYSTEM → Upgrade → Local Upgrade. Upload the firmware file. If the box shipped with 3.x, untick "Keep Settings". Wait for the reboot (3–4 minutes), rejoin the Wi-Fi, log in again. Confirm the version at the bottom of the Overview page.
  4. SYSTEM → Time Zone: set your zone and let it sync when it can.
  5. APPLICATIONS → GoodCloud: leave disabled. NETWORK → UPnP: off. Nothing in this design needs either.
  6. Factory reset, if you ever need it: hold the reset button 10 seconds until the LED flashes fast, then wait for it to go solid. (3 seconds is "repair network", a softer reset.)

The Portal (hallway)

RoleRouter + Repeater. Its WAN is whatever upstream it can find (school Wi-Fi, a hotspot). Its LAN is the 192.168.80.0/24 "core" the Tunnels hang off. Why only this box touches the schoolOne MAC address to authorise on a captive portal, one device to blame, and nothing inside depends on anything the school does.
  1. NETWORK → LAN. Router IP 192.168.80.1, netmask 255.255.255.0. DHCP: start 192.168.80.100, end 192.168.80.199, lease 12 h. Apply. The page goes away; reconnect to the Wi-Fi and open http://192.168.80.1.
  2. WIRELESS → 5 GHz. SSID WormHole-Core, WPA2-PSK, the long backhaul password. Channel: pick a fixed non-DFS channel, 36 or 149 (the Opal does not do DFS radar detection well, so "Auto" can land on a channel it cannot actually hold). Bandwidth 80 MHz is fine. Leave "Hide SSID" off until the Tunnels are joined; you can hide it afterwards if you like (the Tunnels reconnect by name either way).
  3. WIRELESS → 2.4 GHz. Either switch the radio off (nothing needs it) or make it a hallway WormHole with the classroom password so a Pico carried into the hallway still has a home. Fixed channel 6 if you leave it on.
  4. INTERNET → Repeater. Scan, choose the school's student network (at this school it is BYLD, spelled exactly that way; NEXT is the staff 802.1X network and the Opal cannot join it), enter its password, Join. BYLD is open behind a captive portal: join it with no password, on 2.4 GHz (the Portal's 5 GHz radio is the WormHole-Core backhaul and goes quiet if it repeats on 5 GHz). Once connected, open any http site in a new tab from your laptop; the portal login page should appear. Log in. That authorisation is tied to the Portal's WAN MAC, so everything behind it is covered until the portal forgets.
  5. INTERNET → Repeater → the gear icon / Repeater Options. Turn on "Allow Switching to Other Saved Networks". This is the hotspot failover: when the current upstream disappears, it works down the saved list by itself. Turn on "Auto-Enable Login Mode for Public Hotspots" (firmware 4.6+) so the captive portal page is pushed to a client the next time the school portal re-arms. Leave Band Selection on Auto.
  6. Add the hotspots to the saved list. Bring each phone next to the Portal, turn its hotspot on, then on the Portal: Repeater → Scan → join it (password) → it is now saved. Then switch back to the school network (Repeater → Switch Network → Known Networks → pick it). Do this for every phone that should be able to rescue the uplink. Phone settings:
    • Name the hotspot wormsurface (iPhone: Settings → General → About → Name; Android: Hotspot name). Not wormmaster: that name is the Picos' rescue net and every Bin in range would abandon the classroom Wi-Fi for it.
    • iPhone: turn on Maximize Compatibility (2.4 GHz, longer range). Android: set the hotspot band to 2.4 GHz.
    • Give all hotspots the same password so you can type it from memory.
  7. NETWORK → DNS. Mode Automatic. Switch off "DNS Rebinding Attack Protection" (it blocks captive portal pages from loading). Leave "Override DNS for all clients" off.
  8. Address reservations (do this after the Tunnels have joined once, below): NETWORK → LAN → Address Reservation → Add, pick each Tunnel from the dropdown (they show up as GL-SFT1200-xxx) and give them 192.168.80.21, .22, .23 for Tunnel 1, 2, 3. Name them. A Tunnel picks up its reservation the next time it reconnects (toggle its repeater or reboot it).
  9. Check: your laptop on the Portal's Wi-Fi reaches the internet, and http://192.168.80.1 is the Portal.
Captive portals that re-arm daily. Some school portals expire sessions every night or every few days. The runbook has the two-minute fix (open a web page from any laptop on WormHole; the login applies to the Portal's MAC). The Burrows notice the condition themselves: their cloud check gets HTML instead of JSON and reports "captive" on the dashboard.

Tunnel 1, 2, 3 (one per classroom)

RoleRouter + Repeater. Its 5 GHz radio is a client of WormHole-Core (or its WAN port is cabled to the Portal). Its 2.4 GHz radio is the room's WormHole for the Picos and phones. Its LAN port has the Burrow. Why routed, not bridgedThe room keeps its own DHCP, Wi-Fi and Burrow address when the Portal is unplugged. The only cross-room rule it needs is one port forward.

Replace N with the room number (1, 2 or 3).

  1. NETWORK → LAN. Router IP 192.168.8N.1, netmask 255.255.255.0. DHCP start 192.168.8N.100, end 192.168.8N.249, lease 12 h. Apply; reconnect; open http://192.168.8N.1. (The Burrow will be .10, outside the pool, set statically on the Pi.)
  2. WIRELESS → 2.4 GHz. SSID WormHole, WPA2-PSK only (not WPA3 or mixed: the Pico W is happiest on plain WPA2), the classroom password. Fixed channel: 1 for room 1, 6 for room 2, 11 for room 3. Bandwidth 20 MHz. Do not hide it. The Opal lists a maximum of 52 clients; a room is 17 Picos plus phones.
  3. WIRELESS → 5 GHz. Leave it. While the Opal repeats a 5 GHz network its own 5 GHz SSID goes quiet by itself (one radio, one job); you may see it listed but nothing should depend on it. Give it SSID WormHole-5G and the classroom password so a laptop that does find it is harmless.
  4. Backhaul, option A (radio): INTERNET → Repeater. Scan, join WormHole-Core with the backhaul password. Repeater Options: Band Selection 5 GHz, "Allow Switching to Other Saved Networks" off (a Tunnel must never wander onto the school network on its own). Option B (cable): Portal LAN port → this Tunnel's WAN port; the INTERNET page shows "Cable" connected; leave Repeater off.
  5. NETWORK → Port Forwarding → Add. Name Burrow, Protocol TCP, External Port 8080, Internal IP 192.168.8N.10, Internal Port 8080. Enable. This single rule is what lets the other rooms' Burrows mirror this room's data and lets a Pico that lost its own Burrow post here. Optional second rule for remote maintenance from the hallway: 2222 → 192.168.8N.10:22.
  6. On the Portal: reserve this Tunnel's address (192.168.80.2N) as described above, then on the Tunnel toggle the repeater off and on (or reboot) and confirm on the Tunnel's INTERNET page that its WAN address is 192.168.80.2N.
  7. SYSTEM → Security. SSH stays on (default) in case you ever need it; "Open Ports on Router" and admin panel access from WAN stay off (defaults).
  8. Check, from a phone on this room's WormHole: http://192.168.8N.1 is this Tunnel, http://192.168.80.1 is the Portal, and a web page loads from the internet (via Portal → school). From a laptop: ping 192.168.80.2M for another room's Tunnel answers once that Tunnel is up.

Placement and power

  • Portal: hallway, as central to the three rooms as you can, high up (top of a cabinet, not the floor), away from metal. It needs line of sight through at most one wall to each Tunnel. Check the signal from each Tunnel's INTERNET → Repeater page: anything above about −70 dBm is comfortable.
  • Tunnel: wherever the Burrow lives, near the door side of the room if the Portal is in the hall. The Burrow's Ethernet cable goes to the Tunnel's LAN port.
  • Power: all four routers on their own supply, on an outlet that will not be switched off at night. A kicked cord is a designed-for event (everything recovers), but it is still a boring thing to debug the next morning.

If something is off

  • The 2.4 GHz WormHole vanishes while the Tunnel repeats on 5 GHz. A known Opal firmware quirk after some updates (the forum calls it "single-radio AP/STA behaviour"). Reboot the Tunnel first; if it persists, that room's backhaul becomes a cable (Portal LAN → Tunnel WAN) or, failing that, a 2.4 GHz repeater link with both channels fixed.
  • A Tunnel keeps dropping its backhaul. Confirm it is on 5 GHz (Repeater → Band Selection) and the Portal's 5 GHz channel is fixed and non-DFS. The Opal's known weak spot is a 2.4 GHz repeater link; do not use one for the backhaul.
  • The Portal shows "connected, no internet". Captive portal. Open a page from any device behind it and log in. If the page never appears, re-check "DNS Rebinding Attack Protection" is off and that no VPN client is enabled on the Portal.
  • A hotspot does not take over. It must be in the saved list (join it once, manually), "Allow Switching to Other Saved Networks" must be on, and the phone must be in range of the Portal, not of a Tunnel. Walking the phone to the hallway is the whole trick.
  • Picos cannot join. WPA2 only, 2.4 GHz on, SSID exactly WormHole, password matches wifi.json. The Fix a Board page covers the Pico side.
  • Too many clients? The Opal is rated for 52. If a room grows past 20 Bins, reduce the 2.4 GHz bandwidth to 20 MHz (already recommended) and keep phones off it where possible (give phones the hallway WormHole or the 5 GHz SSID).

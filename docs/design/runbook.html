Runbook: install day, every day, and when something is off

Start with the first school visit if that is where you are. Then the order to do things in, what "working" looks like at each step, and the five-minute fixes for everything the failure table predicts. Written for the person who set it all up; the teacher-facing part is the one short list in the middle.

The first school visit: a one-room pilot in under three hours

Two Opals, one Pi 5, three Picos. The only things that must happen at the school are the ones that involve the school: its Wi-Fi, its captive portal, its walls. Everything else is done at home the night before, so the visit is spent testing, not typing.

The night before (about two hours, at home)

  1. Routers (guide): configure the Portal and Tunnel 1 completely, using your home Wi-Fi as the Portal's upstream, and add your phone's wormsurface hotspot to the Portal's saved list. Check: laptop on WormHole reaches the internet, 192.168.80.1 and 192.168.81.1. Then forget your home network on the Portal (Repeater → Known Networks → trash it) so it will not look for it at school.
  2. Cloud (guide): deploy the Surface, bootstrap your admin, import the first three roster lines as teams. Keep gen-secrets.sh's output; you will type the burrow1 token and the live key onto the Pi at school. Create the burrow1 tunnel in Zero Trust and keep its token too. Check: /v1/edge/ping answers with your token. Doing this first turns the visit into the real test: data from a school classroom reaching the cloud through the school network.
  3. Picos (guide): flash all three with tools/fleet/flash.py. They become the first three roster lines (room 1, period 1, bins 1–3). Check each on a phone: its own page, then join your home WormHole (the Tunnel) and watch them appear on… nothing yet (no Burrow): the terminal should say it is trying 192.168.81.10:8080 and moving on. That is correct.
  4. SD cards (guide, steps 1–2): image two cards (one spare) with hostname burrow1, user worm, SSH on. Make the two edits (cmdline.txt token, user-data growpart lines). Do not boot them.
  5. Laptop: repo cloned and pulled, mpremote installed, wrangler logged in, this page open offline (print it or save it). Phone: hotspot named wormsurface, 2.4 GHz compatibility on, charged.
  6. Pack: Portal + Tunnel 1 with their 5 V/3 A supplies; a 27 W Pi 5 supply (the Pis arriving at school may not include one); two imaged microSD cards and the card reader; one Ethernet cable; a USB-C data cable; the three Picos; a power strip; labels; a notebook for the numbers below.

At the school, in order (checks in bold are the reason you came)

  1. Ask or find out: how does the student Wi-Fi authenticate? Open network with a web login (captive portal), a shared password (WPA2-PSK), or username + password per person (WPA2-Enterprise / 802.1X). The Opal joins the first two from the Repeater page. For 802.1X the Repeater join dialog must offer an Enterprise/EAP option; if it does not, the Portal's upstream at this school is a phone hotspot or a wired drop, and that is a design fact to record today, not a failure.
  2. Portal first, in the hallway spot (or where you plan to put it). Power it, join its WormHole-Core from the laptop (or plug the laptop into its LAN port), open 192.168.80.1 → INTERNET → Repeater → join the student network. Open a new browser tab to a plain http site; log into the captive portal if one appears. Check A: the laptop behind the Portal reaches the internet. Then: 
    curl -sS https://whs.makerlabkids.com/v1/edge/ping -H 'authorization: Bearer <burrow1 token>'
curl -sS -o /dev/null -w '%{http_code}\n' https://api.cloudflare.com/
nslookup whs.makerlabkids.com
    Check B: HTTPS to the Worker works and DNS is not rewritten. Note how long the portal session lasts if the school says (a day? a week?).
  3. Tunnel 1 in the classroom. Power it where the Burrow will live. Its repeater should find WormHole-Core by itself. Open 192.168.81.1 → INTERNET: WAN address 192.168.80.21; the Repeater page shows the signal. Check C: signal better than −70 dBm. Write it down. Walk the Tunnel to the far corner and read it again; that is your placement envelope. A phone on WormHole in the room reaches the internet.
  4. Pi 5. Card in, Ethernet to the Tunnel's LAN port, power. Two minutes. Find it in the Tunnel's Clients list, ssh worm@<that address>, then: 
    sudo apt-get update && sudo apt-get install -y git
git clone https://github.com/MakerLabKids/wormhole.git
cd wormhole/edge/burrow && sudo ./setup-pi.sh 1
    (apt goes out through Tunnel → Portal → school: that is Check A again, from a Pi.) Reconnect at 192.168.81.10. Check D: curl -s localhost:8080/health answers and findmnt /data shows the data partition (if it says single-partition mode, note it; it still works for today).
  5. Cloud link from the Pi: write the token and live key (Pi 5 page, step 5), restart the service, then: 
    curl -s localhost:8080/api/status | python3 -c 'import json,sys; c=json.load(sys.stdin)["cloud"]; print(c["reachable"], c["error"])'
    Check E: True None. This is the school network carrying a Burrow upload. Skip cloudflared today unless everything else is done early.
  6. Picos. Power the three (USB from the power strip or the laptop). Within a minute each OLED shows its team name and the Burrow dashboard at http://192.168.81.10:8080/ on your phone shows three tiles. Check F: three tiles, each saying it reports to burrow1.
  7. The failure drills (ten minutes, the most valuable ten of the day):
    • Pull the Tunnel's power. Within about 90 s each Pico's OLED switches to its team hotspot; join one from your phone, open 192.168.4.1, see readings and the 24-hour card. Power the Tunnel, disconnect your phone from the hotspot. Within about three minutes the tiles are back (a board whose hotspot still has a phone on it waits up to ten minutes before looking). Check G.
    • Pull the Pi's power mid-run, plug it back. Thirty seconds later /health answers and the tiles return. Check H.
    • Walk away from the school Wi-Fi with the Portal? You cannot, so do the inverse: on the Portal, Repeater → Switch Network → forget the school network, turn on your phone's wormsurface hotspot next to the Portal. Within two minutes the Pi's cloud.reachable is true again. Re-join the school network afterwards. Check I: the drive-by works.
  8. Twenty minutes after the Picos started: on the website, logged in, the three tiles are on the wall and Admin → Castings lists a verified casting from room 1. Check J: the whole chain, end to end, from a real classroom.
  9. Before leaving: write down the school SSID and auth type, the portal's lifetime, the RSSI numbers at the planned Tunnel spots, which outlets stay on at night, and where the Portal can live. Take the Pi home unlocked; do burrow-lock.sh and cloudflared at home with the other two.

If a check fails

CheckMost likelyDo
A802.1X network, MAC filtering, or the portal page never appearsUse the wormsurface hotspot as the Portal's upstream for the rest of the visit; everything else still gets tested. Record what the school needs (a MAC allow-list entry for the Portal is the usual ask).
BHTTPS blocked or DNS hijackedTry the hotspot path; if the Worker is reachable there but not through the school, the school needs to allow *.makerlabkids.com on 443. Castings keep for years meanwhile.
CWeak backhaulMove the Portal higher or nearer; or run a cable Portal LAN → Tunnel WAN for this room.
Dsetup script stoppedRead its last lines; the partition step tells you to reboot and rerun; apt failures mean Check A did not really pass. Single-partition mode is acceptable for a pilot.
Etoken typo, captive portal re-armed, clock far offcat /etc/burrow/cloud.token; log into the portal again; date (a clock years off makes TLS fail: sudo date -s "$(curl -sI https://cloudflare.com | grep -i ^date: | cut -d' ' -f2-)").
FPicos on the wrong network or wrong passwordTheir terminal (Viper or mpremote connect PORT repl) says which SSID they tried; re-flash one with flash.py --once after fixing the saved Wi-Fi password.
Ghotspot never appearsNote it (this is the one behaviour that could only be proven on real radios); the boards still rejoin and keep posting, and the Burrow's history covers the gap.

Install day, in order

Each step ends with a check that only passes if the previous steps are right. Do not skip a check to save five minutes; it costs an hour later.

  1. Routers at home first (Routers). Configure all four on your kitchen table with your own Wi-Fi as the Portal's upstream. Check: a laptop on WormHole in "room 2" reaches the internet, http://192.168.80.1, and http://192.168.82.1.
  2. Pis at home too (Pi 5 edge). Image, cmdline edit, setup script, one at a time, each wired to its Tunnel. Check: curl http://192.168.8N.10:8080/health for all three, and /api/status on any one shows the other two under peers with ok: true.
  3. Cloud (Cloudflare). Deploy, bootstrap, tunnels, tokens on the Pis. Check: all three tunnels Healthy; a simbins.py --once against burrow1 shows up at whs.makerlabkids.com within a minute; 20 minutes later Admin → Castings shows the casting verified.
  4. Lock the Pis (burrow-lock.sh). Check: findmnt / says overlay; pull a Pi's power, plug it back, it is serving again within 30 s and its castings are intact.
  5. Flash the fleet (Pico fleet). Check: every board shows its team name on the OLED and a tile on the Burrow dashboard; the roster has 50 uids; commit it.
  6. Teams on the Surface. Import the roster CSV, print the cards. Check: log in as one team on your phone over mobile data; the status wall loads in under a second and the Live page ticks.
  7. Move in. Portal in the hallway, Tunnels and Burrows in the rooms, log the Portal into the school's captive portal once from a laptop on WormHole. Check: Tunnel signal to the Portal better than −70 dBm on each; /api/status → cloud.reachable: true on every Burrow.
  8. Hotspot rehearsal. Turn the school uplink off (unplug the Portal's upstream by forgetting it for a moment, or just stand far away), walk a phone with the wormsurface hotspot to the hallway. Within two minutes cloud.reachable flips back to true. Forget nothing: that is the drive-by sync.

For the teacher: the whole thing on one card

  • Normal day: nothing to do. The wall display is http://192.168.8N.10:8080/ (N = your room) on the projector; it needs no login. Students at home use whs.makerlabkids.com with their team card.
  • A tile is grey: that bin's board is not reporting. Check its OLED. If the header shows the team name as a hotspot, it lost Wi-Fi; it will come back by itself, and you can join its hotspot from a phone and open 192.168.4.1 to see it meanwhile. If the screen is dark, check the USB power.
  • Every tile in the room is grey: the room's router (the small white box) lost power, or the Pi did. Check both have lights. Things recover on their own when power returns.
  • The internet badge says "captive": the school Wi-Fi wants a login again. On any laptop or phone connected to WormHole, open a web page, log in to the school portal. Done for everyone.
  • No internet for days: fine. Everything local keeps working and nothing is lost. If someone is passing by the hallway, their wormsurface hotspot uploads the backlog.
  • A student forgot the team passphrase: an admin resets it on the website (Admin → Teams → Reset).
  • Never: unplug the Pi to "fix" something, or factory reset a router. Ask first.

Procedures

Update the Burrow code on a Pi

ssh worm@192.168.81.10
sudo /opt/burrow/burrow-unlock.sh          # reboots writable
ssh worm@192.168.81.10
cd ~/wormhole && git pull && sudo edge/burrow/install.sh
sudo /opt/burrow/burrow-lock.sh            # reboots read-only

Replace a dead Pi or card

Image a new card per the Pi 5 page with the same room number. Put the cloud token and live key back (from your secrets note). It pulls the mirrored history from the other two Burrows within minutes. Lock it.

Re-flash the whole fleet with new firmware

Bump VERSION in lib/picolab.py, run tools/picotest/run.sh, test one board, then tools/fleet/flash.py and plug boards in one by one. Teams are kept by uid.

Rotate a leaked passphrase or token

  • Team passphrase: Admin → Teams → Reset. Takes effect immediately; that team's sessions end.
  • A Burrow token: run tools/gen-secrets.sh for fresh values, npx wrangler secret put EDGE_TOKENS with the new map, write the new token on the Pi (unlock/lock).
  • Live key: new LIVE_KEY secret plus /etc/burrow/live.key on all three Pis.

Export raw data for a science project

Admin → Castings → pick a room and day → download the .jsonl.gz files. One JSON object per line, one line per reading, every field the Bin sent plus the Burrow's timestamp and clock quality. zcat *.gz | python3 -c 'import sys,json; ...' and you are in pandas in two lines. Or, on a Burrow, the same files live under /data/burrow/castings/.

End of semester

Nothing needs deleting; the free tier holds years. If you want a clean slate: Admin → Teams → disable all, and reset the roster's period/bin columns for the new groups (names can carry on or rotate).

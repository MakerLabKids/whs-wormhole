Pico fleet: fifty Bins with names

Every board gets the same firmware, the same worm-bin project, and one team card from the roster. A desk, a USB cable, and about a minute per board: plug in, watch it get a name, unplug, next. Nothing about the sensors, the truth light, the OLED pages, or the dashboard changed; the boards learned three new habits.

What changed on the Pico (and what did not)

Unchanged. projects/worm-bin/main.py is untouched: parts list, hot-plug sensors, POST codes, OLED pages, servos, relay, calibration, /data, /set, /cal. Every other demo project is unchanged too.

Changed: lib/picolab.py (shared by all projects), version 0.1.2. All of it is opt-in through files on the board, so a demo without wifi.json behaves exactly as before.

  • Wi-Fi state machine. The join ladder (wormmaster<n> → wormmaster → WormHole) now runs continuously: lost link → 60 s → own hotspot opens while it keeps scanning every 2 min → rejoin → hotspot closes after 10 stable minutes. Never blocks the sensor loop.
  • Push loop. Every 60 s, a joined board POSTs its /data dict to its Burrow (own subnet .10, then the three Tunnel addresses). "push": false in wifi.json turns it off.
  • History ring. 288 five-minute samples of every numeric reading in RAM, served at /history; the board's own page draws 24-hour graphs from it, hotspot or not.
  • Team card. bin.json gives the board its team, period, bin number and room; name.txt gets the team name, so the hotspot SSID and the wall label are the team.

What you need

  • A laptop with this repo cloned, Python 3, and mpremote: pipx install mpremote (or pip install --user mpremote). Linux, macOS or Windows.
  • A good USB data cable (charge-only cables are the classic time sink).
  • The classroom Wi-Fi password you gave the Tunnels. The script asks once and keeps it in ~/.config/wormhole/wifi-password; it is never written into the repo.
  • Sticky labels, one per board, with the team name. The script prints the name the moment a board is done.

Step 1 · The roster

The roster is tools/fleet/roster.csv: one line per bin, with team, period, bin number and room, plus the board uid once a board has been flashed. Team names come from tools/fleet/names.txt (the Mission Control demo's pool, 142 names, in order) and the room/period layout from tools/fleet/fleet.json:

"rooms": {"1": {"periods": [1, 2], "bins": 17},
          "2": {"periods": [3, 4], "bins": 17},
          "3": {"periods": [5, 6], "bins": 16}}
  1. Edit fleet.json if your periods or counts differ. Reorder or add names in names.txt if you want particular teams to get particular names.
  2. Build the roster (a roster is already committed; rebuild only if you changed the layout): 
    tools/fleet/flash.py --init --force
  3. Open roster.csv in a spreadsheet if you like, but keep the columns. You can swap team names between lines freely until a line has a uid.
  4. Commit it. The roster is the fleet's memory: which physical board is which team. 
    git add tools/fleet/roster.csv && git commit -m "fleet: roster" && git push

Step 2 · The flashing loop

tools/fleet/flash.py

Then, for each board:

  1. Brand-new board: hold BOOTSEL while plugging it in. It mounts as a drive called RP2350; the script notices, copies firmware/RPI_PICO2_W-20260406-v1.28.0.uf2 onto it, and waits for MicroPython to boot. Board that already runs MicroPython (your test units): just plug it in.
  2. The script reads the board's permanent uid. New uid → the next roster line without one. Known uid → that line again, so a re-flashed test unit keeps its team.
  3. It wipes the filesystem (tools/wipe.py, same as the "Fix a Board" page), copies every file the worm-bin project's package.json lists (main.py, index.html, lib/*.py, cal.js), then writes the three identity files: 
    wifi.json   {"ssid": "WormHole", "password": "…", "rescue": "wormmaster"}
bin.json    {"team": "Dirt Vader", "period": 3, "bin": 7, "room": 1}
name.txt    Dirt Vader
  4. It records uid, time and picolab version in the roster, resets the board, and prints ✔ Dirt Vader ready. Label the board. Unplug it.
  5. Plug in the next one. The loop runs until you Ctrl-C. Fifty boards is about an hour.
Order matters only if you want it to. Boards take roster lines top to bottom: room 1 period 1 bin 1 first. If you want a specific board to be a specific team, write its uid into that roster line before flashing (flash.py --check prints a connected board's uid).

Useful variants:

tools/fleet/flash.py --check            # who is this board? uid, name, bin.json, version, files
tools/fleet/flash.py --once             # one board, then exit
tools/fleet/flash.py --port /dev/ttyACM0
tools/fleet/flash.py --dry-run          # rehearse the loop with an imaginary board
cd tools/fleet && python3 -m unittest test_flash   # the roster logic, no hardware

When the roster has its uids, commit it again. Re-running the loop later (a firmware update for the whole fleet) is the same command: every board keeps its team because its uid is known.

Step 3 · First boot, what you should see

  • The OLED opening card, then the usual sensor pages, with the team name as the page header instead of PicoLab742.
  • In the terminal (Viper or mpremote), the banner now includes Team: Dirt Vader (P3 bin 7, room 1) and Pushes: to 192.168.81.10:8080, 192.168.80.21:8080..., and within a few seconds push: Burrow burrow1 at 192.168.81.10:8080 accepted us.
  • On the Burrow dashboard (http://192.168.81.10:8080/) a tile called Dirt Vader appears within 60 s.
  • On the board's own page (its IP, printed in the terminal and shown on the OLED), the status line reads Dirt Vader (P3 bin 7) live on WormHole · reporting to 192.168.81.10:8080, and after ten minutes the "LAST 24 HOURS" card has its first two points.
Check: unplug the Tunnel in that room (or walk the board out of range). Within about a minute the OLED header switches to the team-name hotspot; join it from a phone and open http://192.168.4.1: the page and the 24-hour graphs are there. Plug the Tunnel back in: within about two minutes the board rejoins, the push resumes, and ten minutes later the hotspot goes away by itself.

All of 1–3 use the password in wifi.json. The hotspot (4) is open, as the demos always were.

Changing the firmware later

  • Edit lib/picolab.py or the project; bump VERSION in picolab.py (the OLED and the self-test show it, the roster records it).
  • Run the laptop test first: tools/picotest/run.sh runs the real firmware under the MicroPython unix port with stub radios and a fake clock against a real Burrow, and walks the whole join/lose/hotspot/rejoin story (17 checks). It needs apt install micropython.
  • Then one real board on the bench, then the loop for the fleet. Boards keep their teams.
